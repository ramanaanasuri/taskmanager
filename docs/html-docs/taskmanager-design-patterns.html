Architectural Pattern

Repository Pattern

Abstracting database access behind a clean interface — your code never writes SQL

Architecture diagram — how TaskRepository sits between business logic and database
What this pattern does

The Repository pattern puts a clean abstraction layer between your business logic and the database. TaskController never knows that MariaDB exists. It only calls methods on TaskRepository — Spring Data JPA implements those methods automatically.

Your repo extends JpaRepository<Task, Long> which gives you 18 methods for free: save, findById, findAll, delete, count, and more. You only wrote one custom method — findByUserEmail — and Spring derived the SQL from the method name.

  • Zero SQL written — Spring generates all queries
  • Derived query — findByUserEmail → SELECT * FROM tasks WHERE user_email = ?
  • Swappable DB — switch from MariaDB to PostgreSQL without touching TaskController
  • Testable — mock the repository interface in unit tests without starting a DB

// ── TaskRepository.java ──────────────────────────────────────────────────────
@Repository
public interface TaskRepository extends JpaRepository<Task, Long> {

    // Spring derives SQL from method name — no implementation needed
    // → SELECT * FROM tasks WHERE user_email = :userEmail
    List<Task> findByUserEmail(String userEmail);

    // Inherited from JpaRepository (18 methods, all free):
    // save(T), findById(ID), findAll(), deleteById(ID), count()...
}

// ── TaskController.java — Repository used in 4 endpoints ────────────────────
@RestController
@RequestMapping("/api/tasks")
public class TaskController {

    @Autowired
    private TaskRepository taskRepository;   // only dependency

    @GetMapping
    public ResponseEntity<?> getAllTasks() {
        String email = getCurrentUserEmail();
        List<Task> tasks = taskRepository.findByUserEmail(email);  // ← repository call
        return ResponseEntity.ok(tasks);
    }

    @PostMapping
    public ResponseEntity<?> createTask(@RequestBody Task task) {
        task.setUserEmail(getCurrentUserEmail());
        Task saved = taskRepository.save(task);   // ← INSERT or UPDATE
        return ResponseEntity.status(HttpStatus.CREATED).body(saved);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<?> deleteTask(@PathVariable Long id) {
        Task task = taskRepository.findById(id).orElseThrow(); // ← findById inherited
        taskRepository.delete(task);                           // ← DELETE inherited
        return ResponseEntity.noContent().build();
    }
}
Interview Answer
"Can you explain what design pattern you used for database access and why?"
"I used the Repository pattern via Spring Data JPA. TaskRepository is an interface that extends JpaRepository<Task, Long> — I get 18 CRUD methods inherited for free, including save, findById, and delete. The only method I wrote was findByUserEmail — Spring derives the SQL SELECT * FROM tasks WHERE user_email = ? from the method name. TaskController only depends on this interface, which means I can swap the database from MariaDB to PostgreSQL without changing a single line in the controller, and I can mock the repository in unit tests without starting a real database."

Architectural Pattern

MVC Pattern

Model, View, Controller — three layers, zero coupling between them

MVC layers in Task Manager Pro — Model (Task entity), Controller (Spring Boot), View (React)
Model — Task.java

The Model is Task.java annotated with @Entity. It represents a row in the tasks table. It knows nothing about HTTP or the UI — just data and its constraints.

  • @Entity @Table("tasks") — maps this class to the database table
  • @GeneratedValue — auto-increment primary key
  • @Column(nullable = false) — enforces NOT NULL at JPA level
  • Two constructors: no-arg (required by JPA) and convenience Task(title, email)
Controller — TaskController.java

The Controller handles HTTP routing, auth validation, and response wrapping. It is the only layer that knows about HTTP status codes and request/response shapes.

  • @RestController — combines @Controller + @ResponseBody
  • @RequestMapping("/api/tasks") — all endpoints under this path
  • ResponseEntity<?> — explicit control over HTTP status codes
  • Calls getCurrentUserEmail() before every DB call — enforces ownership
Task.java — the Model Java · JPA Entity

        this.title = title;
        this.userEmail = userEmail;
    }
    // ... getters and setters
}
Interview Answer
"Describe the architecture of your application."
"It follows MVC. The Model is Task.java — a JPA entity mapping to the tasks table in MariaDB. The Controller is TaskController.java — it handles HTTP routing, validates that the authenticated user owns the resource, and returns ResponseEntity with the appropriate status codes. The View is the React frontend — it calls the REST API and renders the data. Each layer has a single responsibility. The controller never writes SQL. The model never knows about HTTP. The React frontend never contains business logic."

Behavioral Pattern

Chain of Responsibility

Every HTTP request passes through a chain of filters — your JWT filter is one link

Filter chain — request flow from browser to TaskController
What Chain of Responsibility means here

Spring Security builds a chain of Filter objects. Each filter does its job, then calls filterChain.doFilter() to pass the request to the next handler. If a filter decides to reject the request, it writes the response directly and does not call doFilter — the chain stops.

Your JwtAuthenticationFilter is one link in this chain. It was inserted before UsernamePasswordAuthenticationFilter by this line in SecurityConfig:

http.addFilterBefore(jwtAuthenticationFilter,
  UsernamePasswordAuthenticationFilter.class);
The critical line — passing the chain

The most important line in JwtAuthenticationFilter is the last one. Whether the JWT is valid or not, the filter always calls:

filterChain.doFilter(request, response);

If the JWT was valid, SecurityContext is already set, and the downstream filter will see an authenticated user. If the JWT was missing or invalid, SecurityContext is empty, and Spring Security's authorization check will return 401 before the request reaches TaskController.

This is the Chain of Responsibility contract — do your job, then pass it on.

JwtAuthenticationFilter.java Java · Spring Security Filter 
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    @Autowired
    private JwtTokenProvider tokenProvider;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                        HttpServletResponse response,
                                        FilterChain filterChain)
            throws ServletException, IOException {
        try {
            String jwt = getJwtFromRequest(request);   // extract Bearer token

            if (StringUtils.hasText(jwt) && tokenProvider.validateToken(jwt)) {
                String email = tokenProvider.getEmailFromToken(jwt);

                // Build authentication object and set it in SecurityContext
                UsernamePasswordAuthenticationToken authentication =
                    new UsernamePasswordAuthenticationToken(
                        email, null,
                        Collections.singletonList(new SimpleGrantedAuthority("ROLE_USER"))
                    );
                authentication.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
                SecurityContextHolder.getContext().setAuthentication(authentication);
            }
            // If JWT missing or invalid: SecurityContext stays empty → Spring returns 401

        } catch (Exception ex) {
            logger.error("Could not set user authentication in security context", ex);
        }

        // ── CHAIN OF RESPONSIBILITY: always pass to next filter ──────────────
        filterChain.doFilter(request, response);   // ← THE critical line
    }
}
Interview Answer
"How does your JWT filter work and what pattern does it use?"
"JwtAuthenticationFilter is an implementation of the Chain of Responsibility pattern. Spring Security builds a chain of Filter objects. My filter extends OncePerRequestFilter — which guarantees it runs exactly once per request — and is inserted before UsernamePasswordAuthenticationFilter. It extracts the Bearer token, validates the HMAC-SHA256 signature using JwtTokenProvider, extracts the email claim, and sets it in SecurityContextHolder. The critical line is filterChain.doFilter() at the end — whether authentication succeeded or not, I always pass control to the next filter. If auth failed, the SecurityContext is empty, and Spring's authorization layer returns 401 before the request reaches TaskController."

Behavioral Pattern

Strategy Pattern

Two interchangeable authentication strategies — JWT for APIs, OAuth2 for browser login

Strategy pattern — same interface, two concrete implementations, SecurityConfig picks at runtime
Why Strategy fits here

You have two ways to authenticate a user: they can call an API with a Bearer token (JWT strategy), or they can log in via a browser using Google or Facebook (OAuth2 strategy). Both produce the same outcome — an authenticated user in SecurityContext — but the mechanics are completely different.

The Strategy pattern lets you swap the algorithm without changing the caller. SecurityConfig selects which strategy applies based on the request type. TaskController does not know or care which strategy ran — it just reads getCurrentUserEmail() from SecurityContext.

  • Both strategies share the same AuthenticationSuccessHandler interface contract
  • SecurityConfig is the context that wires both strategies in
  • Adding a third strategy (e.g. API key auth) requires zero changes to TaskController
Two OAuth2 success handlers — a note

Your codebase has two OAuth2 success handlers: OAuth2AuthenticationSuccessHandler and OAuth2LoginSuccessHandler. Both implement the same pattern but were written at different stages of the project.

OAuth2AuthenticationSuccessHandler — implements AuthenticationSuccessHandler directly. Registered in SecurityConfig as the active handler.

OAuth2LoginSuccessHandler — extends SimpleUrlAuthenticationSuccessHandler (higher abstraction). Uses UriComponentsBuilder for URL construction.

Note: SecurityConfig uses OAuth2AuthenticationSuccessHandler. OAuth2LoginSuccessHandler appears to be an older version. Consider removing it to avoid confusion.

OAuth2AuthenticationSuccessHandler.java + SecurityConfig.java Java · Strategy Pattern 
// ── Strategy B — OAuth2AuthenticationSuccessHandler.java ─────────────────────
@Component
public class OAuth2AuthenticationSuccessHandler
        implements AuthenticationSuccessHandler {   // ← same interface contract

    private final JwtTokenProvider jwtTokenProvider;

    @Value("${frontend.url}")
    private String frontendUrl;

    @Override
    public void onAuthenticationSuccess(
            HttpServletRequest request,
            HttpServletResponse response,
            Authentication authentication) throws IOException {

        // Generate JWT from the OAuth2 user's Google/Facebook profile
        String jwt = jwtTokenProvider.generateToken(authentication);

        // Redirect browser to React frontend with the JWT in query param
        String target = frontendUrl + "/oauth2/redirect?token=" +
                URLEncoder.encode(jwt, StandardCharsets.UTF_8);
        response.sendRedirect(target);
    }
}

// ── Context: SecurityConfig.java — wires both strategies ─────────────────────
http
    // Strategy B: OAuth2 browser login
    .oauth2Login(oauth -> oauth
        .successHandler(oAuth2AuthenticationSuccessHandler))

    // Strategy A: JWT API auth — runs before default password filter
    .addFilterBefore(jwtAuthenticationFilter,
        UsernamePasswordAuthenticationFilter.class);
Interview Answer
"How did you handle having two different authentication mechanisms?"
"I used the Strategy pattern. There are two authentication strategies: JwtAuthenticationFilter handles stateless API calls by reading a Bearer token from the Authorization header. OAuth2AuthenticationSuccessHandler handles browser-based login via Google or Facebook. Both plug into Spring Security through the same interface contract. SecurityConfig acts as the context — it wires both strategies in and Spring picks the right one based on the request type. TaskController is completely unaware of which strategy ran — it just reads the email from SecurityContext. Adding a third strategy, like API key auth, would require zero changes to any controller."

Behavioral Pattern

Template Method Pattern

Spring defines the skeleton — you fill in one specific step

Template Method — abstract class defines the algorithm, your subclass fills one step
What Template Method gives you

The Template Method pattern defines the skeleton of an algorithm in a base class and lets subclasses override only the specific step they care about. Spring uses this extensively.

OncePerRequestFilter handles the boilerplate: checking if the request has already been filtered this thread, handling async dispatch correctly, and managing the servlet lifecycle. Your code fills in exactly one method: doFilterInternal.

  • Spring guarantees once-per-request execution — you don't write that logic
  • You override only doFilterInternal — the hook point
  • The base class calls your override at the right moment
  • Hollywood Principle: "Don't call us, we'll call you"
OAuth2LoginSuccessHandler — same pattern

OAuth2LoginSuccessHandler extends SimpleUrlAuthenticationSuccessHandler, which is itself a Template Method implementation. The base class handles redirect strategy, response-committed checking, and URL determination. You override onAuthenticationSuccess to inject JWT generation.

// The base class calls getRedirectStrategy()
getRedirectStrategy().sendRedirect(request, response, targetUrl);
// You don't implement redirect logic — inherited
Interview Answer
"Why does JwtAuthenticationFilter extend OncePerRequestFilter instead of implementing Filter directly?"
"OncePerRequestFilter is a Template Method implementation from Spring. It defines the algorithm skeleton: it checks if the filter has already run for this request on this thread, handles async dispatch edge cases, and manages the servlet lifecycle. I only override doFilterInternal — my JWT validation logic. This is the Hollywood Principle: Spring calls my code at the right moment; I don't need to manage the outer algorithm. The practical benefit is that my filter is guaranteed to run exactly once per request, even in complex async scenarios, without me writing that logic."

Structural Pattern

Singleton Pattern

Spring creates one instance of every @Component and @Bean — shared across all requests

Spring ApplicationContext as Singleton registry — one instance, injected everywhere
How Spring implements Singleton

You never call new JwtTokenProvider(). Spring's ApplicationContext creates one instance at startup, stores it in its bean registry, and injects that same reference wherever it's needed. This is the Singleton pattern — managed by the container, not by getInstance().

  • @Component — registers the class as a bean, scope=singleton by default
  • @Configuration + @Bean — factory method beans, also singleton
  • @Value — injected once at startup from application.properties
  • JwtTokenProvider is shared by 3 other beans — same object in memory
Thread safety consideration

Singletons are shared across all concurrent requests. This means your singleton beans must be stateless or thread-safe. JwtTokenProvider reads jwtSecret and jwtExpiration at construction and never modifies them — it is inherently stateless and thread-safe.

If you stored mutable state in a singleton (e.g. a counter or a cached list that changes) without synchronization, you would have a race condition. Your current beans are safe because:

  • JwtTokenProvider — reads @Value fields, generates new objects per call
  • SecurityFilterChain — configuration-only, immutable after build()
  • TaskController — all state is per-request via method params
Interview Answer
"What is the Singleton pattern and where does it appear in your code?"
"Every @Component and @Bean in my Spring Boot app is a singleton by default. JwtTokenProvider is annotated @Component — Spring creates one instance at startup, injects the jwt.secret property once, and then reuses that exact object everywhere: in JwtAuthenticationFilter, in OAuth2AuthenticationSuccessHandler, and in AuthController. I never write getInstance() — the container manages it. The key design requirement for singletons is thread safety — since all HTTP requests share the same JwtTokenProvider instance concurrently, it must be stateless. Mine is: it reads immutable @Value fields and creates new return objects on every call, so there is no shared mutable state."

Structural Pattern

Dependency Injection

Spring wires every dependency — your classes never construct their own collaborators

Constructor injection — SecurityConfig (preferred)

SecurityConfig uses constructor injection — the recommended style. All three dependencies (OAuth2 handler, JWT filter, JWT token provider) are declared as constructor parameters. Spring resolves and injects them when creating the SecurityConfig bean.

Constructor injection is preferred because: dependencies are explicit and mandatory, the class cannot be created in a broken state, and it is easier to test by passing mock objects directly.

Field injection — TaskController (@Autowired)

TaskController uses @Autowired field injection. Spring sets the field directly after creating the object via reflection. This is simpler to write but has drawbacks: the dependency is implicit, the class can be constructed without it in tests, and it cannot be made final.

For a controller that is unlikely to be unit-tested without Spring context, @Autowired field injection is acceptable. For core services and security infrastructure, constructor injection is the right choice.

SecurityConfig.java + TaskController.java — two injection styles Java · Dependency Injection 
// ── STYLE 1: Constructor Injection — SecurityConfig.java ─────────────────────
// Dependencies are explicit, mandatory, and immutable
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtAuthenticationFilter;
    private final OAuth2AuthenticationSuccessHandler oAuth2AuthenticationSuccessHandler;
    private final JwtTokenProvider jwtTokenProvider;

    // Spring sees this constructor and injects all three from its registry
    public SecurityConfig(
            OAuth2AuthenticationSuccessHandler oAuth2AuthenticationSuccessHandler,
            JwtAuthenticationFilter jwtAuthenticationFilter,
            JwtTokenProvider jwtTokenProvider) {
        this.oAuth2AuthenticationSuccessHandler = oAuth2AuthenticationSuccessHandler;
        this.jwtAuthenticationFilter = jwtAuthenticationFilter;
        this.jwtTokenProvider = jwtTokenProvider;
    }

    // @Value injection — from application.properties
    @Value("${frontend.url}")
    private String frontendUrl;

    @Value("${cors.allowed-origins}")
    private String corsAllowedOrigins;
}

// ── STYLE 2: Field Injection — TaskController.java ────────────────────────────
// Simpler syntax, but dependency is implicit
@RestController
public class TaskController {

    @Autowired                          // Spring sets this field after construction
    private TaskRepository taskRepository;
}
Comparison: Constructor vs Field injection
Aspect Constructor Injection (SecurityConfig) Field Injection (TaskController)
Immutability Fields can be final — guaranteed set once Cannot be final — Spring uses reflection
Testability Pass mocks via constructor — no Spring needed Requires Spring context or reflection to inject mocks
Null safety NPE impossible — Spring fails at startup if missing NullPointerException possible at runtime
Circular deps Detected at startup — fast fail May be masked until runtime
Verbosity More boilerplate One annotation — concise
Interview Answer
"What is Dependency Injection and how did you apply it?"
"Dependency Injection means my classes declare what they need and Spring provides it — they never use 'new' to create their own collaborators. I used two styles. SecurityConfig uses constructor injection: all three dependencies are constructor parameters, which means they're final, mandatory, and testable by passing mocks directly. TaskController uses @Autowired field injection for simplicity. The trade-off is that constructor injection is safer — Spring fails at startup if a dependency is missing — while field injection can produce a NullPointerException at runtime. For security infrastructure I always prefer constructor injection. I also use @Value injection to pull jwt.secret and frontend.url from application.properties, keeping configuration out of code."

Security Pattern

JWT + OAuth2 Token Pattern

Stateless auth — no session, no DB lookup per request, HMAC-SHA256 signed tokens

Complete auth flow — from OAuth2 login to every subsequent API call
JWT token structure — what's inside

JwtTokenProvider.generateToken() builds a JWT with three parts: header (algorithm), payload (claims), and signature. Your token contains:

// HEADER
{ alg: "HS256", typ: "JWT" }

// PAYLOAD (claims)
{ sub: "user@gmail.com",
  email: "user@gmail.com",
  name: "User Name",
  picture: "https://...",
  iat: 1700000000, exp: 1700086400 }

// SIGNATURE
HMAC-SHA256(base64(header) + "." + base64(payload), jwtSecret)
Why this is stateless — the key benefit

Traditional session auth stores user state server-side and looks up a session ID on every request — this means a DB call per request. JWT flips this: the user identity is embedded and cryptographically signed in the token itself.

  • No DB lookup per request — identity extracted from token in memory
  • No server-side session — SessionCreationPolicy.STATELESS in SecurityConfig
  • Scalable — any AWS/GCP instance can validate without shared session store
  • Tamper-proof — HMAC-SHA256 signature fails if payload is modified
  • Facebook picture — your code handles nested map structure: map.get("data").get("url")
JwtTokenProvider.java — token generation and validation Java · JJWT · HMAC-SHA256 
@Component
public class JwtTokenProvider {

    @Value("${jwt.secret}")
    private String jwtSecret;          // must be 32+ chars for HMAC-SHA256

    @Value("${jwt.expiration}")
    private long jwtExpiration;          // millis — e.g. 86400000 = 24h

    private SecretKey getSigningKey() {
        byte[] keyBytes = jwtSecret.getBytes(StandardCharsets.UTF_8);
        return Keys.hmacShaKeyFor(keyBytes);   // HMAC-SHA256 key
    }

    public String generateToken(Authentication authentication) {
        OAuth2User principal = (OAuth2User) authentication.getPrincipal();

        String email = principal.getAttribute("email");
        String name  = principal.getAttribute("name");

        // Facebook returns picture as a nested map — handled here
        Object pictureObj = principal.getAttribute("picture");
        String pictureUrl = null;
        if (pictureObj instanceof Map<?,?> map) {
            Object data = map.get("data");
            if (data instanceof Map<?,?> dataMap)
                pictureUrl = dataMap.get("url").toString();
        }

        return Jwts.builder()
                .subject(email)
                .claim("email", email)
                .claim("name", name)
                .claim("picture", pictureUrl)
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + jwtExpiration))
                .signWith(getSigningKey(), Jwts.SIG.HS256)  // ← signs with secret
                .compact();
    }

    public boolean validateToken(String authToken) {
        try {
            Jwts.parser()
                .verifyWith(getSigningKey())   // verifies HMAC-SHA256 signature
                .build()
                .parseSignedClaims(authToken); // throws if expired or tampered
            return true;
        } catch (JwtException | IllegalArgumentException ex) {
            return false;                      // covers: expired, malformed, wrong sig
        }
    }
}
Interview Answer
"Explain your authentication architecture end to end."
"My app supports two entry points. For browser login: the user clicks Google or Facebook login, Spring redirects to the OAuth2 provider, the provider returns an auth code, Spring exchanges it for user info, and OAuth2AuthenticationSuccessHandler generates a JWT signed with HMAC-SHA256 containing the user's email, name, and picture as claims. The JWT is URL-encoded and sent to the React frontend via redirect — the frontend stores it in memory. For every subsequent API call: the frontend sends Authorization: Bearer <token>. JwtAuthenticationFilter validates the HMAC-SHA256 signature using the same secret key, extracts the email claim, and sets it in SecurityContextHolder. TaskController reads that email to scope all database queries to the authenticated user. There is no server-side session — SessionCreationPolicy.STATELESS — so this scales horizontally across any number of AWS or GCP instances without a shared session store."
